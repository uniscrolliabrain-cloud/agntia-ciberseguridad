# Decisiones de implementación · 2026-11-10

Autor: agente implementador, ejecución solicitada por el propietario. Se conserva el diseño de investigación y no se toca `/agente`.

1. **Una instalación privada, un nodo, un worker de API, SQLite WAL.** `BEGIN IMMEDIATE`, FKs por tenant, UNIQUE por identidad de activo, backups antes de DDL y auditoría transaccional. Se han probado dos procesos inicializando; esto no habilita un despliegue distribuido. No se ha configurado cifrado de disco ni gestión externa de backups.
2. **Principal servidor y bearer opaco por referencia de entorno.** Cada binding tiene rol, tenants, caducidad y revocación. Este servicio es la audiencia de esas credenciales; no se acepta un JWT o header arbitrario de `/agente`. Producción requerirá gateway/TLS privado y el contrato de identidad verificado. No hay dueño local implícito. Una nueva configuración requiere reinicio; las operaciones revalidan el registro cargado y los valores actuales de sus referencias.
3. **Registro, consentimiento del titular y revisión separados.** Un administrador configura recursos y evidencia de representación, y un segundo principal revisor aprueba el hash de la propuesta. Este proceso no verifica por sí mismo la autenticidad jurídica de un consentimiento: el administrador debe custodiarla. `emergency_contact_ref` prepara el contacto de escalado. Datos reales y perfiles activos siguen deshabilitados por alcance de campaña.
4. **DTOs futuros sin ejecución futura implícita.** Job/Finding/Evidence/Approval/BudgetReservation se exportan como contratos cerrados. Todavía no hay workers, reservas de coste ni almacenamiento de resultados. El límite declarado en un grant limita una solicitud de preflight; no es un contador agregado de gasto.
5. **Registro de activo antes del snapshot.** D1P5 congela el hash de la configuración, no el contenido de un repo. Snapshot, protección frente a cambios/symlinks durante lectura y sandbox corresponden a D2. Ningún scanner está invocable en esta entrega; no se permite interpretar el preflight como autorización para ejecutar procesos del host.
6. **Ficheros consolidados por responsabilidad.** `auth.py` incluye capacidades y tenancy; `service.py` reúne inventario/grants; `storage.py` reúne migración/auditoría. Se evita crear wrappers vacíos solo para reproducir rutas propuestas por el plan. Separarlos cuando la complejidad lo justifique.
7. **Auditoría defendida por triggers y hashes.** El servicio no ofrece modificar/borrar eventos. Los triggers impiden SQL UPDATE/DELETE accidental; una autoridad con acceso al fichero puede quitar triggers y reescribir todo. Falta anclaje externo del último hash. La prueba de manipulación simula explícitamente ese acceso privilegiado.
8. **Errores y entradas limitados antes de negocio.** Máximo 64KiB, 256 frames y cinco segundos totales por body; cabeceras ambiguas se rechazan; JSON inválido no se refleja. TLS, rate limiting y tamaño global de cabeceras corresponden al reverse proxy de despliegue, todavía no habilitado.
9. **No se convierten gates futuros en PASS.** Docker local denegado; no se usa shell del host como sustituto de sandbox. CI de Python verifica el núcleo, no ejecuta Docker ni audita software de clientes. La revisión independiente de D1P6 queda diferenciada de la revisión realizada por el propio implementador.
10. **Publicación revisable.** Rama `feat/cyber-d1-foundation`, PR contra main. No merge/despliegue automático. El ZIP de documentación de main sigue siendo un snapshot histórico y no contiene estos cambios de runtime.
