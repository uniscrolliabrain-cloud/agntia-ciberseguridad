# Decisiones de las fases 6–10

1. **Orden e identificación.** Fase6=D1P6;7=D2P1;8=D2P2;9=D2P3;10=D2P4. Se desarrollan componentes y contratos sintéticos sin afirmar que sus dependencias de release estén cerradas. No se habilita ejecución de clientes por haber escrito el código o pasado una fixture.
2. **Revisión independiente.** No existe un segundo revisor acreditado en esta entrega. El catálogo, threat model y revisión propia dejan D1P6 parcial. `ReleaseGates` deniega por defecto y `StaticScanner` lo exige; la API no ofrece ruta de ejecución de scanners. Los valores positivos de los tests son fixtures explícitas, no una aprobación inventada.
3. **Adquisición local POSIX.** Se copia una raíz aprobada mediante descriptores y O_NOFOLLOW; no se ejecuta Git, hooks, filtros, LFS, submódulos o instalación. Remote clone, imagen y extracción de archivos permanecen unsupported. Un archivo comprimido puede copiarse como bytes acotados, nunca se extrae en el host. Git commit=null es deliberado; se conserva content_hash del árbol capturado.
4. **Snapshot congelado, no filesystem transaccional.** Contenido de copia con hashes, permisos de lectura y mount read-only en worker. Se detectan cambios durante cada lectura y enumeración; no se promete un punto instantáneo común entre todos los archivos de un origen que sigue modificándose. Para esa garantía hará falta un commit Git aprobado o snapshot del filesystem. El administrador del host sigue siendo una autoridad de confianza.
5. **Custodia aditiva.** Migración2 registra snapshot, tenant, asset, grant y hashes. Un directorio huérfano no se admite por ID. Rename y SQLite no comparten transacción distribuida: fallo normal revierte y limpia; un crash puede dejar un huérfano no visible que requiere conciliación posterior. Backup/upgrade desde versión1 probado, sin borrar auditoría.
6. **Launcher y worker separados.** El launcher de confianza usa el daemon local y nunca recibe shell del agente. El scanner no tiene Docker socket, credenciales ni red. La API no debe alojar el launcher privilegiado. Perfil fijo: UID65532, cap-drop, no-new-privileges, root/input read-only, tmpfs noexec, CPU/RAM/pids/timeout/salida acotados y sin logging crudo del daemon.
7. **Sin proxy heredado dentro del scanner.** El cliente offline del launcher usa un DOCKER_CONFIG temporal vacío, sin modificar el del equipo, para que Docker no inyecte proxies del host en cada contenedor. No se envía entorno global ni bearer al proceso analizado.
8. **Procedencia y licencias.** Binarios oficiales8.30.1/2.7.1 con SHA256 de releases. Se construyen imágenes scratch y se referencian por image ID inmutable. Config/reglas tienen hash separado. Gitleaks core/defaults MIT; OSV Apache2.0; notices incluidos. No se usa la action comercial Gitleaks ni se adquiere un servicio. Feeds externos y MSSP requieren revisión específica antes de un piloto comercial.
9. **Resultados minimizados.** Gitleaks descarta Secret/Match/Description/Author y crea fingerprint de ubicación/regla/snapshot, no del secreto. OSV no infiere explotación, reachability, severidad o licencias ausentes. SBOM observado CycloneDX1.5; validación completa con esquema oficial y otros ecosistemas queda pendiente.
10. **Caché offline separada.** Solo se monta una caché aprobada read-only; hash/fecha/ecosistemas se verifican. El test real usa una DB inventada y diminuta, no un feed representativo de cobertura productiva. No se instalan paquetes del cliente ni se usa fix/resolve. Los configs del repo no pueden añadir ignores al perfil administrado.
11. **Correcciones con evidencia.** Fixture de probe0700 no era legible por UID65532: se corrigió la fixture, no el UID ni el mount. Overflow podía bloquear `Process.wait()` al abandonar una tubería llena: drenaje acotado que descarta sobrante, mata el CLI y limpia el contenedor, con regresión de proceso sintético local y test Docker.
12. **Publicación.** Rama `feat/cyber-phases-06-10` y PR#2 apilada sobre PR#1. No tocar main, /agente, compras o producción. El ZIP histórico no se regenera como si fuese un instalador actualizado.
